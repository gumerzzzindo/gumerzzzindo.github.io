## Herramientas necesarias

```bash
gcc --version      # GCC 11+ o cualquier versión reciente
objdump --version  # binutils, viene con GCC
```

También puedes usar [Compiler Explorer (godbolt.org)](https://godbolt.org) si no quieres instalar nada: pegas C, eliges compilador y flags, y ves el ASM en tiempo real.

## El experimento base

Trabajaremos con una función sencilla. Guárdala como `demo.c`:

```c
#include <stdio.h>

int suma(int a, int b) {
    return a + b;
}

int factorial(int n) {
    int resultado = 1;
    for (int i = 2; i <= n; i++) {
        resultado *= i;
    }
    return resultado;
}

int main(void) {
    printf("%d\n", factorial(suma(3, 4)));
    return 0;
}
```

Compilamos dos veces:

```bash
gcc -O0 -fno-pie -o demo_O0 demo.c
gcc -O2 -fno-pie -o demo_O2 demo.c
```

Y desensamblamos:

```bash
objdump -d -M intel demo_O0 > O0.asm
objdump -d -M intel demo_O2 > O2.asm
```

## -O0: el ensamblador literal

Con `-O0` GCC no optimiza nada. Cada variable local tiene una dirección en la pila. Cada operación se carga en un registro, se hace y se guarda de vuelta. Es verboso pero predecible.

La función `suma` con `-O0`:

```nasm
suma:
    push   rbp
    mov    rbp, rsp
    mov    DWORD PTR [rbp-0x4], edi   ; guarda 'a' en pila
    mov    DWORD PTR [rbp-0x8], esi   ; guarda 'b' en pila
    mov    edx, DWORD PTR [rbp-0x4]   ; carga 'a'
    mov    eax, DWORD PTR [rbp-0x8]   ; carga 'b'
    add    eax, edx
    pop    rbp
    ret
```

Nueve instrucciones para `return a + b`. Esto es lo que ves en binarios sin strip cuando el código no está optimizado (debug builds, algunos malware amateur).

El patrón clave: **todo pasa por la pila**. Los argumentos se leen desde `[rbp-N]` aunque ya estaban en registros. Es redundante, pero hace que el debugging sea trivial: cada variable tiene una dirección fija.

## -O2: el ensamblador real

Con `-O2` GCC activa la mayoría de optimizaciones que no aumentan el tamaño del binario. La función `suma` desaparece:

```nasm
main:
    sub    rsp, 0x8
    mov    edi, 0x7          ; factorial(7) directamente
    call   factorial
    mov    esi, eax
    lea    rdi, [rip+fmt]
    xor    eax, eax
    call   printf
    xor    eax, eax
    add    rsp, 0x8
    ret
```

`suma(3, 4)` se evalúa en tiempo de compilación: el compilador sabe que `3 + 4 = 7` y lo reemplaza por la constante. Esto se llama **constant folding**. La función `suma` no aparece en el binario porque solo se llama con valores constantes —es **inlined** y luego eliminada.

## Optimizaciones que debes reconocer

### 1. Inlining

El compilador sustituye la llamada a una función por el cuerpo de esa función directamente. Resultado: no ves `call suma` en el binario, ves las instrucciones de `suma` pegadas donde estaba el call.

Señales en Ghidra: una función "sin nombre" con lógica que debería ser una llamada, o múltiples bloques con el mismo código pero sin función compartida.

### 2. Loop unrolling

Un bucle corto se desenrolla: en vez de iterar N veces, el compilador escribe N copias del cuerpo.

```c
for (int i = 0; i < 4; i++) buf[i] = 0;
```

Con `-O2` puede convertirse en:

```nasm
mov    DWORD PTR [rbx],   0x0
mov    DWORD PTR [rbx+4], 0x0
mov    DWORD PTR [rbx+8], 0x0
mov    DWORD PTR [rbx+c], 0x0
```

No hay `jmp`, no hay contador. Si ves bloques de escrituras consecutivas sin saltos, sospecha de unrolling.

### 3. Strength reduction

El compilador reemplaza operaciones costosas por equivalentes más baratas.

| C original | ASM -O0 | ASM -O2 |
|---|---|---|
| `x * 4` | `imul eax, eax, 4` | `shl eax, 2` |
| `x * 8` | `imul eax, eax, 8` | `lea eax, [eax*8]` |
| `x / 2` (unsigned) | `div 2` | `shr eax, 1` |
| `x % 8` (unsigned) | `idiv` | `and eax, 7` |

Cuando veas un `lea` con un multiplicador raro (`lea eax, [rax+rax*4]` = `x*5`), es casi siempre una multiplicación optimizada.

### 4. Dead code elimination

```c
int debug_mode = 0;
if (debug_mode) {
    printf("debug info\n");
}
```

Con `-O2` el `if` y el `printf` desaparecen del binario. En reversing esto significa que **la ausencia de código también es información**: si esperas ver un check pero no está, quizás el compilador lo eliminó porque la condición siempre es falsa.

### 5. Tail call optimization

```c
int f(int n) {
    if (n == 0) return 1;
    return n * f(n - 1);
}
```

Si el compilador puede demostrar que la llamada recursiva es lo último que hace la función, convierte el `call` + `ret` en un `jmp`. Esto rompe el stack frame esperado y puede confundir a los decompiladores.

## Factoria con -O2: el bucle transformado

```nasm
factorial:
    cmp    edi, 1
    jle    .Lret_one
    mov    eax, 1
    mov    ecx, 2
.Lloop:
    imul   eax, ecx
    add    ecx, 1
    cmp    ecx, edi
    jle    .Lloop
    ret
.Lret_one:
    mov    eax, 1
    ret
```

Comparado con `-O0`, el compilador:
- Usa registros directamente (`ecx` como contador, `eax` como acumulador) sin tocar la pila
- Reorganiza la condición del bucle para evitar un salto extra al inicio
- El prólogo/epílogo (`push rbp` / `pop rbp`) desaparece porque no necesita frame pointer

## Flujo de trabajo en Ghidra

Cuando abres un binario en Ghidra y ves código desensamblado, Ghidra intenta descompilarlo a C. Pero el C que muestra es una **aproximación**: el decompilador reconstruye variables locales y estructuras de control a partir del ASM, y a veces se equivoca.

Pasos recomendados:

1. **Mira el ASM primero**, no el decompilador. El ASM es la verdad.
2. Identifica el prólogo/epílogo para saber qué usa el frame pointer y cuántas variables locales hay.
3. Busca los patrones de arriba: `shl`/`shr` para multiplicaciones, `lea` con multiplicadores, bloques repetidos para unrolling.
4. Usa el decompilador como punto de partida, no como fuente definitiva.

Para comparar tu C con el output real sin instalar nada:

```
https://godbolt.org  →  C/C++  →  x86-64 gcc  →  -O0 / -O2
```

## Ejercicio práctico

Crea este archivo y compílalo con `-O0` y `-O2`:

```c
#include <string.h>

int buscar(const char *haystack, char needle) {
    int len = strlen(haystack);
    for (int i = 0; i < len; i++) {
        if (haystack[i] == needle) return i;
    }
    return -1;
}
```

Preguntas que debes poder responder mirando el ASM:

1. ¿Dónde está `len` en la versión `-O0`? ¿Y en `-O2`?
2. ¿Qué hace el compilador con `strlen` en `-O2`?
3. ¿Cuántos registros usa cada versión?

Usa `objdump -d -M intel` y compara. Si te atascas, pégalo en Godbolt con ambos flags.

## Resumen

| Situación | Pista |
|---|---|
| Muchos `mov [rbp-N]` consecutivos | Build sin optimizar (`-O0`) |
| Función que esperabas y no existe | Inlined o dead code elimination |
| `shl`/`shr` en vez de multiplicar | Strength reduction |
| Bucle sin contador visible | Loop unrolling |
| `jmp` donde esperabas `call`+`ret` | Tail call optimization |
